PREGUNTA 1: ¿Cómo se define o usa la tabla 'police_members'?
────────────────────────────────────────────────────────────

DEFINICIÓN:
  • Archivo: schema.sql (línea 81-94)
  • Migración: supabase/migrations/001_police_system.sql (línea 30-43)
  
  CREATE TABLE IF NOT EXISTS police_members (
    discord_id TEXT PRIMARY KEY,
    username TEXT,
    role_id TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
  );

USO:
  • Propósito: Control de acceso (verificar permisos Discord)
  • No contiene: rango, departamento (eso está en payroll_members)
  • Patrón: UPSERT (insert or update) con ON CONFLICT (discord_id)

FUNCIONES ASOCIADAS:
  • add_police_member(p_discord_id, p_username, p_role_id)
    → Se llama después de verificar rol en Discord

PREGUNTA 2: ¿Qué columnas tiene realmente esa tabla?
─────────────────────────────────────────────────────

EXACTAMENTE 4 COLUMNAS:

┌─ Columna 1: discord_id (TEXT, PRIMARY KEY) ──────────────────────┐
│                                                                   │
│ ID único del usuario en Discord                                  │
│ Ejemplo: "123456789012345678"                                    │
│ Uso en código:                                                   │
│   • Filtro principal: eq.                            │
│   • En INSERT: requiere valor                                    │
│   • En SELECT: proyecto frecuente para verificación             │
│ Ubicaciones: 37 referencias en el código                         │
│                                                                   │
└───────────────────────────────────────────────────────────────────┘

┌─ Columna 2: username (TEXT, NULLABLE) ────────────────────────────┐
│                                                                   │
│ Nombre de usuario Discord                                        │
│ Ejemplo: "AdminUser"                                             │
│ Puede ser NULL (aunque en práctica se asigna siempre)           │
│ Uso en código:                                                   │
│   • Filtro: ilike. (búsqueda difusa, case-insensitive) │
│   • En INSERT: asignado junto a discord_id                      │
│   • SELECT: frecuente para mostrar nombre de usuario            │
│ Ubicaciones: developer.html (búsqueda), manage.html (listado)   │
│                                                                   │
└───────────────────────────────────────────────────────────────────┘

┌─ Columna 3: role_id (TEXT, NOT NULL) ────────────────────────────┐
│                                                                   │
│ ID del rol de Discord que autoriza acceso                        │
│ NO es el rango policial (eso está en payroll_members)           │
│ Es el rol del servidor Discord                                   │
│                                                                   │
│ Valores típicos y su significado:                                │
│   • "1431255106212335686" = POLICE (acceso general al MDT)      │
│   • "1502940172348690482" = MANAGE (administración de turnos)   │
│   • "1425697670495862844" = DEV (herramientas de desarrollo)    │
│   • "1430728225423884419" = FOUNDATION (fundación)              │
│                                                                   │
│ Uso en código:                                                   │
│   • Filtro: eq. (búsquedas de autorización)            │
│   • SELECT: frecuente para verificar permisos                   │
│   • Nunca se actualiza directamente (solo add_police_member)   │
│ Ubicaciones: auth.js (verificaciones), dashboard.html, itmdt.html
│                                                                   │
│ PROBLEMA POTENCIAL:                                              │
│   No hay índice en role_id → búsquedas por rol son lentas       │
│                                                                   │
└───────────────────────────────────────────────────────────────────┘

┌─ Columna 4: created_at (TIMESTAMPTZ, NOT NULL, DEFAULT NOW()) ───┐
│                                                                   │
│ Timestamp de creación automático                                 │
│ Ejemplo: 2026-11-06 15:30:45.123456+00:00                       │
│ Generado automáticamente (no asignar en INSERT)                  │
│ NO se accede en código (información solo de auditoría)           │
│                                                                   │
└───────────────────────────────────────────────────────────────────┘

IMPORTANTE: police_members NO tiene:
  ✗ rank (rango) - está en payroll_members
  ✗ department (departamento) - está en payroll_members
  ✗ status - no existe en el schema
  ✗ hire_date - está en payroll_members

PROBLEMA REPORTADO: "Query a police_members falla o se queda cargando"
───────────────────────────────────────────────────────────────────────

CAUSAS PROBABLES (en orden de probabilidad):

1. SIN ÍNDICES (85% de probabilidad)
   ─────────────────
   Problema: No hay índice en columns role_id o username
   
   Síntoma: Queries lentas especialmente:
     • Búsqueda por role_id (dashboard.html)
     • Búsqueda por username ILIKE (developer.html)
   
   Solución: Crear índices
     CREATE INDEX idx_police_members_role_id ON police_members(role_id);
     CREATE INDEX idx_police_members_username ON police_members(username);


2. CARGA MASIVA TRUNCADA (10% de probabilidad)
   ──────────────────────────
   Problema: manage.html línea 86 usa limit: '1000'
   
   Si hay > 1000 registros:
     • No da error
     • Silenciosamente trunca datos
     • Frontend no sabe que hay más datos
   
   Solución: Reducir límite o implementar paginación
     const members = await supaSelect('police_members', '*', { limit: '500' });


3. TIMEOUT EN SUPABASE (3% de probabilidad)
   ──────────────────────
   Problema: PostgREST timeout (default 30s)
   
   Síntoma: Query en manage.html cargando indefinidamente
   
   Solución: Implementar cancellation o timeout en frontend


4. LOCKS EN LA TABLA (1% de probabilidad)
   ──────────────────
   Problema: Transacción abierta bloqueando writes
   
   Diagnóstico: Ejecutar en SQL Editor
     SELECT * FROM pg_locks 
     WHERE relation = (SELECT oid FROM pg_class WHERE relname = 'police_members');


5. RLS POLICY ISSUE (1% de probabilidad)
   ────────────────
   La política es simple USING (true), poco probable pero posible
